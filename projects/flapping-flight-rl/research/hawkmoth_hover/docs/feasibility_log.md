## IBAMR IIM prescribed-motion capability audit (2026-10-02)

**Question.** Can the pinned IBAMR 0.19.0 immersed-interface `IIMethod` replace the failing point-force penalty path for the existing zero-thickness prescribed wing without first adding a method extension?

**Source evidence.** The pinned `IIMethod.h` describes a finite-element surface mesh and exposes initial coordinate mapping, initial velocity, and optional tangential-velocity-motion registration. It does not expose a time-dependent prescribed-motion registration. In `IIMethod.cpp`, forward Euler, midpoint, and trapezoidal structure updates advance coordinates using interpolated fluid velocity (or its tangential component). The `use_direct_forcing` input branch instead copies current coordinates to new coordinates in all three updates, holding the surface fixed during that step. The 3-D IIM examples inspected are coupled FSI/flexible-surface setups; they do not implement a prescribed rigid-wing trajectory.

**Decision.** IIM is a better geometric starting point for a zero-thickness surface than stock `ConstraintIBMethod`, because it is explicitly formulated on a discrete surface mesh and does not use CIB's occupied-cell-derived per-point volume correction. However, it is not a drop-in prescribed-wing implementation: following a time-varying rigid transform requires an application or solver-strategy extension, and that extension must consistently impose prescribed interfacial velocity and corresponding force/jump data at IIM's time levels. This source audit does not establish that such an extension is correct or that IIM will pass any Stage A flow gate.

The immutable source audit is `results/stage_a_iim_prescribed_motion_audit_local_20261002_v4/iim_prescribed_motion_audit.json`; its manifest records the audit-script and four pinned source/example hashes. It was run with `tools/audit_iim_prescribed_motion.py`. It is source inspection only: no IIM build, example run, new solver run, or acceptance-gate change occurred. Stage A remains **FAILED / UNVALIDATED**.


**Constraint-force finding (expanded source trace).** `IIMethod::computeLagrangianForce()` initializes the surface force at each quadrature point to zero, adds only registered surface-pressure and surface-force callback contributions, integrates that force, and derives the pressure/velocity-gradient jumps from it. The stock code does not solve an unknown surface multiplier to satisfy `J_h u = U_prescribed`; `use_direct_forcing` only changes the coordinate update. Thus setting the coordinates to a desired pose by itself would not establish no-slip. A mathematically credible prescribed-wing IIM route needs a constrained fluid/interface solve (or an equivalently verified iterative coupling) that determines interface traction while enforcing the prescribed surface velocity at consistent time levels, then verifies the resulting pressure and viscous jump signs and global momentum exchange. The expanded finding and callback/jump source excerpts are recorded in the v4 machine-readable audit; it remains a source-based implementation requirement, not a proven unique design.

### DG-IIM source-level force-accounting audit and output repair (2026-10-03)

A pinned IBAMR 0.19.0 code audit resolved some field semantics. `target_force_function` reads IIM FE velocity and contributes the prescribed surface force to IIM's force/jump construction. With pressure and velocity jumps both active, the callback is represented through pressure/velocity-gradient jumps; it is not an unknown multiplier enforcing no-slip. `use_direct_forcing` copies the current coordinates and freezes the mesh, without setting the Eulerian boundary velocity. `TAU_OUT` is IBAMR's exterior-side traction (`WSS_OUT-P_OUT*n`); a closed-body reference example integrates it as body force. For the current open disk it represents one oriented side only; a total thin-sheet force and its sign remain unqualified until both sides and independent momentum are accounted for.

The old “spring reaction” output integrated and negated the full callback, so it included the velocity-feedback term whenever `ETA_S` was nonzero. Its `[m/s]`, `[m^2]`, and `[m]` labels were unsupported. The postprocessor now prints spring, velocity-feedback, and total registered IIM callback integrals separately; reports `TAU_OUT` explicitly with its mesh-normal orientation; and labels all quantities as code units. Rebuilt `ETA_S=0` and `ETA_S=100` runs reproduce prior flow metrics to printed precision; at ETA 100 the spring term is zero and the velocity term equals the combined callback integral. No hydrodynamic force claim follows.

Source semantics and remaining limits are detailed in `docs/iim_force_accounting_audit.md`; exact solver/source/build/run provenance is indexed by `results/open_disk_force_audit_local_20261003_v1/artifact_manifest.json`. ### Prescribed-velocity coupling route screen: CIB pilot recommended (2026-10-03)

Pinned IBAMR 0.19.0 source shows `CIBStaggeredStokesSolver` solves a coupled saddle-point system containing fluid velocity, pressure, a constraint Lagrange multiplier, and (when free) rigid-body velocity. `CIBMethod` uses standard rigid-body IB markers and evaluates user-prescribed COM translation/angular velocity at current, midpoint, and new times. This is compatible in principle with the project's fixed-shape prescribed-wing stage. The installed `libIBAMR3d.dylib` exports both CIB classes (SHA-256 `ad92cffa2c1450ee20eb392aac4874dfdb1fc6db2102f8f48f03dd2e19e40cc9`).

The pinned `examples/CIB/ex0` demonstrates fully prescribed kinematics in 2-D; 3-D CIB examples demonstrate rigid marker bodies, but no inspected pinned example demonstrates fully prescribed 3-D open-sheet behavior. CIB's default per-marker regularization field equals Eulerian cell volume; optional weight files divide that value by per-marker weights. This is solver regularization, not physical wing thickness. Marker-density, edge, and resolution behavior on the existing open sheet remain unknown. The separate `ConstraintIBMethod` has an occupied-cell-derived volume heuristic; it is not the selected candidate and must not be conflated with `CIBMethod`.

# Geometry lineage audit: 1998 male-*Manduca* virtual wing vs. 2012 hover model

**Status:** documentary comparison complete; coordinate-level comparison not possible from the source artifacts currently available. The generated-geometry manifest has a stale input hash, but the point clouds were independently regenerated byte-for-byte from the current checked-in outline. No geometry, mesh, solver input, or prior run was changed. No CFD was run.

## Decision

Keep the intended paired-wing planform lineage tied to Nakata & Liu (2012) for the planned 2012 hover comparison. Do not replace it with a hand-traced 1998 planform from an uncalibrated figure, and do not describe either model as a measured, specimen-linked *Manduca sexta* 3-D wing. The two sources describe different geometric lineages, and the 1998 source does not supply a machine-readable surface or numerical thickness. Before the next geometry-bearing run, correct the manifest metadata or record the verified current input hash in that run’s immutable manifest; the existing checked-in point clouds were regenerated successfully from the checked-in outline in this audit.

This is a **geometry-lineage decision only**. It does not clear the unresolved immersed-boundary/Brinkman method, pass Stage A, authorize a hover run, or establish a biological validation result. For a specifically anatomical *Manduca* geometry claim, obtain specimen-linked measured geometry or a source-authorized, sufficiently resolved figure and digitize it with a declared scale and uncertainty before changing the model.

## Evidence and provenance

### 1998 Liu et al. virtual wing

The paper reports that the virtual-wing planform was based on tracing the forewing and hindwing outlines of a **male *M. sexta***. It reports aspect ratio 5.3, uniform thickness, and elliptical smoothing at the leading edge, trailing edge, and tip. The simulation uses a single virtual paired-wing representation; the described fore/hind components meet along a co-axis. Separately, the hover-kinematic reference quantities are reported as mean chord 18.3 mm, wing length 48.3 mm, stroke amplitude 2 rad, and frequency 26.1 Hz. The paper does not establish that those kinematic dimensions and its male planform trace belong to the same measured individual.

The text and Fig. 3 caption do **not** provide outline coordinates, scale bars tied to a specimen, a CAD/surface mesh, numeric thickness, a thickness distribution, or a specimen identifier. “Uniform thickness” is a modeling statement, not a measured anatomical thickness. The Fig. 3 depiction is a schematic planform and grid illustration; it is not a numerical geometry release. The accessible article record/full-text representation available for this audit did not provide a source raster suitable for calibrated digitization. Accordingly, no 1998 outline CSV or 3-D surface was fabricated.

### 2012 Nakata & Liu hover-model lineage in this repository

The repository’s reference-data ledger records the 2012 paper as combining paired fore/hind outlines traced from *Agrius convolvuli* and scaling the mean chord to the *Manduca* reference. Its figure also presents a CFD model and a separate CSD model; the CSD thickness colors/section are not an executable, specimen-linked surface definition for the CFD wing. The local `wing_outline.csv` is explicitly a 10-station **manual visual estimate** of Fig. 1(b), not author-provided coordinates. It has no image-to-axis transform or uncertainty model. The project geometry generator applies spanwise linear interpolation and isotropic in-plane scaling to reach the selected mean chord; it makes a thin surface point cloud and contains no measured thickness.

The local source files and their status are described in `reference_data/README.md`. This audit leaves those source files and generated `case/geometry` points untouched. A direct SHA-256 check found that current `reference_data/wing_outline.csv` hashes to `663645bb297fc1b7a1e3044da3941e04638864b6aa5b8db09d91ba9a4926f07b`, while `case/geometry/geometry_manifest.json` declares input hash `7d829a55686d02eb5048ef10352239d52836b35276e72d12d54ba25f7653c328`. This is a real stale-manifest defect. To test whether it obscures the point-cloud lineage, I generated both wing files in a temporary directory with the checked-in generator and current CSV at the recorded 0.75 mm spacing. Both outputs matched the checked-in `.vertex` files byte-for-byte and matched their declared point-cloud hashes. Thus the point clouds are reproducibly derived from the current outline despite the incorrect input-hash field; the manifest should be refreshed before a future geometry-bearing run.

## Global geometry check

This check tests only compatibility of global proportions; it does not establish planform identity.

| Quantity | Current project representation | 1998 source | Interpretation |
|---|---:|---:|---|
| Semi-span / wing length, `R` | 48.3 mm (generator constant) | 48.3 mm reported for the hover case | Same nominal scale used by this project; not proof of a shared specimen |
| Mean chord, `c̄` | 18.3 mm target (generator constant) | 18.3 mm reported for the hover case | Current outline is scaled to this value by construction |
| One-side planform area | `R c̄ = 883.89 mm²` by definition of the generator’s scaling | Not independently tabulated as a digitized tracing in the source text | Generator target follows published-scale values; not a direct measurement |
| Bilateral aspect ratio, `(2R)² / (2S_one) = 2R/c̄` | 5.2787 for the generator’s nominal `R` and `c̄` | 5.3 reported | Agreement is effectively imposed by using the same nominal `R` and `c̄`; it is only a bookkeeping/global-scale check, not independent shape validation |
| Current source-outline maximum chord | At `s/R = 0.48`; 1.2888 times its spanwise mean | Figure shows shape but gives no tabulated stations | Metric is from the current checked-in outline and does describe the checked-in surface generated by the recorded script/settings |

The project’s tabulated current chord widths, before final dimensional scale, are 0.22, 0.48, 0.68, 0.82, 0.89, 0.87, 0.77, 0.51, 0.25, and 0 across the ten listed span stations. These are values in the hand-traced outline’s arbitrary shape coordinates, not measurements from either moth specimen. Their attribution to the existing point clouds is supported by the byte-for-byte regeneration check; the manifest input-hash field nevertheless needs correction.

## What would permit a true figure-to-figure comparison

The minimum missing artifact for the 1998 comparison is a lawfully accessible high-resolution raster of Fig. 3A (or its underlying tracing), plus a documented calibration convention. A defensible digitization would preserve the source file and hash, crop bounds, pixel-to-coordinate transform, landmarks, tracing procedure, and uncertainty from line width and scale. It would then report normalized chord distributions and area moments against the hash-pinned current 2012 trace. Such digitization would remain a reconstruction of a published schematic, not specimen-linked 3-D anatomy; a numeric thickness still requires separate source evidence or an explicitly assumed sensitivity bracket. The existing geometry manifest’s input hash is a separate metadata correction to make before the next geometry-bearing run.

For an anatomical geometry rather than figure reconstruction, the needed source is specimen-linked 3-D wing surface data or sufficient measured planform and cross-sectional thickness data, including specimen identity, sex, measurement protocol, and uncertainty. The current sources do not provide that package.

# Jigglypuff project audit — September 25, 2026

The project has a useful asynchronous training foundation and an agent that beats several level-9 CPUs. Its current training distribution, controller vocabulary, and evaluation coverage do not support a claim of superhuman play. More hours with the existing configuration would not resolve several structural limitations.

The recommended direction is a Jigglypuff specialist initialized from strong human replay data, refined against a diverse population of learned opponents, with complete mechanics, stage coverage, and independent human evaluation. Reuse the current emulator supervision and dashboard where useful. Investigate integrating Slippi-AI before rebuilding its data and opponent infrastructure.

This audit reviewed the active `puffbot` source, tests, saved configuration, training logs, checkpoint identities, and both saved evaluation reports. It ran the existing tests and additional temporary synthetic probes. No training, checkpoint promotion, source changes, or new Dolphin matches were performed. Native gameplay consequences of the controller findings still need direct validation.

## Findings, ordered by importance

### 1. The opponent population cannot teach broad competitive play

**Structural limitation, high priority.** Every learned opponent is the current Puff or a historical Puff. Fox, Falco, Marth, etc. are only built-in CPUs. Once the pooled level-9 frontier is declared mastered, self-play rises from 20% to 60%, making most new opponents Puffs. That is useful for the ditto, but does not supply increasingly strong Fox or Falco adversaries.

The frontier pools characters and advances on 26 wins in a rolling 40-game window. It does not require minimum coverage or success for each matchup. Repeated rolling checks are a curriculum heuristic, not a statistical certification. `mastered` also remains true if subsequent results deteriorate. Historical selection keeps a recency-limited set rather than selecting policies for strategic diversity or exploitability.

**Improve:** add an opponent interface supporting independently trained character policies and external agents. Start with strong Fox, Falco, Marth, Sheik, Falcon, Peach, and Puff opponents, then expand to the full roster. Track a matchup-by-policy payoff matrix. Allocate extra training to reliably measured weaknesses, retaining easy opponents and old exploiters for regression coverage. Train some opponents explicitly to find ways to beat the current Puff. Preserve historical strategies based on usefulness rather than age alone. A restricted-population mixture is a robustness tool, not proof of a global Nash equilibrium.

### 2. Controller restrictions remove useful competitive techniques

**Verified input limitation, high priority.** Ordinary airborne states allow no macro containing L, R, Z, or an analog shoulder input. The shield safety rule consequently removes fresh airborne inputs for L-cancelling and tech attempts, alongside intentional air dodges. Avoiding accidental offstage air dodges is sensible; removing all these inputs creates a ceiling.

Two consecutive full-jump macros also produce twelve uninterrupted frames of Y. They do not create a second button press. The current test checks one macro in isolation and misses this sequence. Native validation should confirm the effect across jump states and timing.

Long macros cannot be interrupted by a new policy decision for up to sixteen frames. The vocabulary also has coarse directional precision and forbids all sufficiently offstage Rest attempts. These restrictions are design choices; they should be measured rather than described as universally optimal Puff play.

**Improve:** build explicit state-aware L-cancel and tech inputs, reliable jump release/press transitions, jump-budget-aware recovery, adjustable aerial drift, and one-frame defensive/punish decisions where needed. Permit deliberate risk through appropriate actions rather than globally forbidding it. Verify input sequences in actual Dolphin at different percentages, velocities, hitlag states, and stage positions.

A practical architecture is a policy choosing goals or techniques with a verified low-level executor for precise inputs. A more flexible alternative is a joint/autoregressive controller policy, initialized from replays; avoid returning to independent uniformly random button heads.

### 3. Evaluations can be marked finished without the requested evidence

**Reproduced correctness defect, high priority.** The evaluator sets `state='finished'` after workers end without checking that each quota was met. A mocked worker-exit path produced a finished report with zero games out of ten requested.

A related worker path returns after the first Sudden Death timeout, abandoning the remaining games in its setup. A synthetic five-game setup produced only one result. The evaluator schedules a fixed number of setups, so timeout-heavy policies can underfill the sample. Retrying an entire setup after an error can also repeat already-completed games without durable attempt identifiers.

The evaluator records the observed CPU level but accepts results into the requested-level aggregate without validating a match. The actual 60-game report had no such mismatch, so this is a latent defect, not grounds to discard those results.

**Improve:** give every scheduled game a unique ID; require exact quotas; preserve every attempt and interruption; use bounded retries; distinguish completed, incomplete, failed, and cancelled evaluations. Validate character, stage, port, stocks, timer, and CPU level. Freeze the checkpoint once, hash it, and save the full protocol and environment/source identity. Make champion promotion require a complete qualifying report.

### 4. Final Destination and a partial roster are hard limits

**Verified coverage limitation.** Configuration rejects every other stage. Edge geometry is hard-coded and observations have no platform geometry. Sheik is explicitly absent from the default roster; Ice Climbers and several others are absent too. Supporting Ice Climbers also requires representing Nana rather than only one entity per opposing port.

**Improve:** support and test the stage set for the intended competition rules, including platforms, ledges, blast zones, slopes and transformations where applicable. Add reliable Sheik selection/transform handling. Introduce all-character coverage, with character-specific entities and projectiles. Randomize and evaluate both ports/spawn sides. Make matchup and stage coverage visible in the dashboard.

### 5. Observations omit information and the policy cannot remember it

**Reproduced observation aliasing.** Projectiles contain only relative position and presence. Two projectiles at the same position but with opposite velocities and different types yield identical observations. There is no sequence model to infer motion from recent frames. The single-frame feed-forward model also cannot directly retain repeated opponent habits, previous defensive choices, or adaptation across a set.

The earlier project's ineffective LSTM, described in this README, does not establish that recurrence is unnecessary. Its failure could have been a training or integration issue.

**Improve:** include projectile velocity/type/ownership, additional relevant entities, stage features, input history and timing state that is actually available to the deployed agent. First compare a short frame stack against a small GRU; move to a larger sequence model only if controlled evaluations justify it. A longer-lived opponent-context state can be explored separately from short-term mechanics memory. Keep hidden state reset/burn-in correct across games and fragments.

### 6. The objective is short-sighted and its shaping guarantee is overstated

**Verified configuration and mathematical discrepancy.** Gamma is 0.997 **per frame**. Its half-life is **3.85 seconds**, not the 5.5 seconds documented in the comment; 5.55 seconds is approximately its exponential time constant. An outcome 30 seconds away has weight 0.00448; at 60 seconds the weight is 0.0000201. This does not make long-term learning impossible, but heavily favors near-term returns over patient stock/set strategy.

For three-frame actions, lambda=0.95 produces a direct trace time constant around 0.83 seconds on-policy. This is not the complete value-function horizon, because bootstrapping carries estimates beyond the trace.

The potential term is skipped on stock loss/dead-state transitions. Therefore it is not consistently `gamma * Phi(next) - Phi(current)` across a full trajectory, despite the policy-invariance claim. Two synthetic paths with identical start/end states, duration, and stock loss returned -0.997 versus -1.28045 depending on the offstage path. The existing test intentionally expects no death refund, so it cannot prove the advertised invariant. This is evidence of an additional path-dependent death penalty, not evidence that the observed bot is farming rewards.

**Improve:** explicitly decide between policy-invariant shaping and deliberate recovery penalties. Implement terminal/death boundary handling consistently and audit total reward components. Compare longer physical-time discount horizons and weaker damage shaping under matched compute and multiple seeds. Ensure game-result and stock outcomes dominate the final intended objective. Test useful edgeguards and stock trades, not just recovery safety.

### 7. Runtime and experiment reproducibility need another pass

**Reproduced:** `max_game_frames` only normalizes an observation; the game loop does not enforce it. A synthetic match ran for 160 frames with a configured cap of 30. Per-frame deadlines do not stop a game that keeps delivering frames forever. Classify a safety-cap termination separately from a legitimate game timeout.

**Other code findings:** supervision checks process liveness rather than stale progress; behavior staleness is checked on queue receipt but not again when a pending fragment is consumed; evaluation uses current local configuration rather than a saved checkpoint protocol; compatibility metadata covers action names but not observation encoding, timing, or script semantics. Full-checkpoint restore bypasses even that action-contract check. Changing code with identical action names can silently change what saved weights mean. No Git repository exists in this project directory.

The logs include broken streams and shutdown warnings about leaked semaphores. These deserve a bounded soak test and resource measurements; warnings alone do not establish a persistent live resource leak. Measured policy lag was at most two updates in the saved metrics, and stale-fragment drops were zero, so off-policy lag is not the first suspect here.

**Improve:** enforce match and job deadlines; add progress-based watchdogs; retain interrupted trajectory metadata and avoid treating emulator failure as a genuine terminal game state; version the full environment/observation/action contract; record source hashes, config, seeds and emulator/ISO/Gecko identity. Archive RNG state for meaningful resumes. Protect checkpoints referenced by evaluation reports from time-based pruning.

## Recommended routes

| Route | Assessment | First decision test |
|---|---|---|
| Replay initialization + learned opponent population + recurrent RL | Best overall direction. Supplies competent mechanics and realistic opponents, then permits improvement beyond demonstrations. | Build a held-out replay baseline and demonstrate actual improvement against independent opponents. |
| Integrate or build on Slippi-AI | Strong candidate for avoiding duplicated data, model, and opponent work. Compatibility, Puff quality, latency and host support remain to be measured. | Run a pinned upstream model locally, verify Puff support and other-character opponents, then benchmark adapters and deployment delay. |
| Verified skill executor + learned strategic policy | Practical for this Mac and good for targeted Puff technique reliability. Hard-coded skills can still create blind spots. | Compare recovery, landing, defensive and punish success over a diverse scenario suite and full games. |
| Expanded pure RL from scratch | Possible research path, but costly exploration; requires richer actions, broader opponents and much better validation first. | Compare several seeds at matched trained frames against replay-initialized agents. |
| Simulator/search-assisted training | Potentially valuable later. Simulator fidelity and simultaneous-action uncertainty are significant risks. | Reproduce short native-Dolphin trajectories before using simulator rollouts to teach a policy. |

Slippi-AI's current README describes human replay imitation followed by self-play RL, a released model covering twelve characters, and human play tools. Its architecture document describes recurrent/transformer cores and autoregressive controller heads. Its README also acknowledges a faster decompilation-based simulator. These are reasons to investigate reuse, not evidence that it is a drop-in superhuman Jigglypuff or that its simulator is suitable for this deployment. [Slippi-AI](https://github.com/vladfi1/slippi-ai), [architecture](https://raw.githubusercontent.com/vladfi1/slippi-ai/main/ARCHITECTURE.md).

A league should include adversaries that deliberately discover weaknesses, rather than only historical copies of the main learner. AlphaStar supplies a precedent for diverse league training; PSRO supplies a framework for learning responses to mixtures of policies. Neither gives a convergence guarantee for this finite-compute Melee implementation. [AlphaStar](https://deepmind.google/blog/alphastar-mastering-the-real-time-strategy-game-starcraft-ii/), [PSRO paper](https://arxiv.org/abs/1711.00832).

The original Melee RL paper demonstrated professional-level performance under its particular conditions, but explicitly describes restricted controller inputs and simplified match handling. It should not be used as evidence that any restricted vocabulary will generalize to all matchups. [Original Melee RL paper](https://willwhitney.com/assets/papers/Beating.the.Worlds.Best.pdf).

## Execution order and acceptance criteria

1. **Make comparisons trustworthy.** Freeze and hash the 48.17M evaluated candidate and the final candidate. Fix evaluation quotas, timeout accounting, interruption records and full protocol capture. Require every scheduled cell to complete; never promote on an incomplete report. Retain stochastic deployment evaluation and separately measure greedy decoding. Greedy play is not inherently stronger in a competitive game.
2. **Repair and verify mechanics.** Test press/release sequences, airborne L-cancel and tech inputs, recovery, and interruptible actions in native Dolphin. Build scenarios covering Rest confirms, missed-Rest punishment, throw follow-ups, DI, shield pressure, edgeguards and offstage recovery. Count actual successful techniques, not only action selections. Reserve some scenarios for testing.
3. **Supply strong opponents and replay data.** Assess upstream integration. Split demonstrations by player/session/event, balance matchups, preserve state/input timing, and evaluate on unseen players. Use discrete action distributions rather than averaging incompatible controller choices. Replay initialization need not impose a permanent imitation constraint; compare scheduled or adaptive regularization and save its cumulative progress across resumes.
4. **Expand state, stages and league.** Add projectile dynamics, additional entities, a short history model, actual stage geometry, missing characters, both ports and exploiters. Select training opponents using measured difficulty with a coverage floor. Reserve opponents and seeds for final validation.
5. **Run controlled experiments.** Compare current baseline, repaired mechanics, richer observations/history, replay warm start and multi-character league under matched budgets. Use multiple independent seeds where feasible. Then sweep horizon/reward choices. Log actual emulator frames, player-frames, learner utilization and accepted data separately before adding hardware.
6. **Validate deployment and human strength.** Measure observation-to-input latency at real time. Decide and publish whether the target permits machine reaction speed or imposes a human-like delay; decision interval alone is not reaction delay. Use the same information/input restrictions in training and evaluation. Add human-controller/netplay support, then run recorded consented sets against increasingly strong players and invited exploit attempts.

Suggested CPU screening can start at 40–100 games per important matchup with port/seed coverage; this is a screening budget, not certification. For claims about humans, predeclare opponents, stages, set format, latency and success thresholds, report per-matchup results and uncertainty, and treat human sessions as correlated rather than assuming every game is an independent draw. Keep exploit-discovery players separate from the final held-out panel.

No finite benchmark can establish “beats anyone.” A credible target is sustained wins against a diverse expert field across the supported competition rules, with no known reproducible exploit after deliberate testing. The immediate priorities are evaluation correctness, controller completeness, and stronger multi-character opponents; a larger network or another uninterrupted CPU-training run comes after those.
